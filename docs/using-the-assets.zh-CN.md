# 使用发布的资产

[English](using-the-assets.md)

本文写给已发布站点的读者：浏览、下载或链接导出器所发布文件的人，以及读取这些文件的程序。它说明每种视图、每种文件是什么，怎样引用文件才能长期有效，以及音频与视频相对游戏原始流损失了多少，并附上这些结论背后的测量和复现方法。文件是怎样产出的，见[对象与资产](objects-and-assets.zh-CN.md)和[发布](publishing.zh-CN.md)。

## 版本与地址

游戏的每次更新都会发布为一个新版本，已发布的版本永不改变。下面的地址沿用[服务](serving.zh-CN.md#路由)中示例的路由；站点也可以使用其他写法。

| 地址 | 指向 |
|---|---|
| `/{region}@{version}/{path}` | 某个已发布版本中的文件。其内容永不改变，可以放心引用并长期缓存 |
| `/{region}/{path}` | 当前版本中的同一文件，随每个新版本更新 |
| 以 `/` 结尾的路径 | [目录列表](serving.zh-CN.md#目录)：该目录下直接包含的子目录与文件，JSON 格式 |
| 目录树路由，如 `/trees/{region}/{view}` | 整个视图的[目录树](spec/directory-tree.zh-CN.md)，一份 gzip 压缩的文档 |
| 版本历史或变更路由 | 视图的[版本历史](spec/version-history.zh-CN.md)，以及某个版本新增、删除、改动了哪些文件 |

浏览整个视图的页面先读一次目录树，再按路径读取同一版本中的文件，目录树和文件就不会来自两个版本。

## 视图

| 视图 | 内容 |
|---|---|
| `storage` | 网页直接使用的文件，按游戏的资源路径排列：图片同时提供无损 PNG 和体积更小的有损 WebP，音频为 MP3，视频为 MP4（[storage 视图](spec/storage-view.zh-CN.md)） |
| `canonical` | 每个资产按其运行时读取的形式写出：一份资产文档 `<name>.asset.json` 和若干成员文件。模型是 glTF，动作和曲线是 JSON 文档。供需要还原游戏表现的程序使用（[发布](spec/publication.zh-CN.md)） |
| `client` | 随安装包发布、不经下载的资源，例如称号框和界面精灵，按游戏加载它们的路径命名 |

## 只导出有明确使用方的产物

每一种资产形式都对应一个写明的使用方，例如网页本身、3D 服装查看器、MySekai 预览、Live2D 查看器、剧情播放器。形式只保留这个使用方需要的数据，规范写清每个字段从游戏的哪里来、是什么意思，并用测试与游戏对照。

所以这里没有原样倒出的 Unity 对象。没有使用方的字段，没人能验证它对不对，它的结构也会随游戏版本悄悄变化；读者还得自己去理解 Unity 的序列化细节。

资源包里没有被任何形式认领的对象不会被默默丢掉，而是记为“未知”留在运行的导出记录里，等有了明确的使用方再为它定义形式。形式为何由运行时决定，见[对象与资产](objects-and-assets.zh-CN.md#资产形式的定义者)。

## 为什么不以 Unity 编辑器为目标

Unity 编辑器确实可以当作兜底的使用方：把所有对象还原成一个 Unity 工程，什么都能打开。导出器没有走这条路：

- 编辑器不是网页。浏览器、查看器和各种脚本都读不了 Unity 工程，最后仍然要为每个使用方另写转换。
- 打开工程需要特定版本的 Unity 和它的专有许可；这里的产物都是开放格式（PNG、MP3、MP4、glTF、JSON），任何环境都能读。
- 还原工程要同时处理脚本、着色器和包依赖，大部分与展示无关，而且没法逐项证明正确。宁可少做，但每种产物都能和游戏逐项对照。
- 每个版本都完整导出成工程，体积和更新成本都远超按需导出的形式。

|---|---|
| `*.asset.json` | [资产文档](spec/asset-documents.zh-CN.md)：这个资产属于哪种形式、来自哪个资源包的哪些对象、有哪些成员文件，以及它的指纹 |
| `*.glb` | glTF 二进制[模型](spec/model.zh-CN.md)。网格、骨骼和贴图引用之外，材质参数和节点在游戏里的来源写在 `extras` 里 |

| `*.moc3` | Live2D 模型文件，与游戏中存储的字节完全相同 |
| `physics.json`、`*.physics3.json` | Live2D 物理设置，与游戏中存储的字节完全相同 |
| `motion/*.json`、`facial/*.json` | [Live2D 动作](spec/live2d.zh-CN.md)：淡入淡出时间，加上它播放的 Unity 动画 clip，写作 [clip 文档](spec/clip-documents.zh-CN.md) |
| `cues.json` | [音频](spec/audio.zh-CN.md)资产的 cue 表：每个 cue 播放哪些波形、长度、循环区间、音量和编排 |
| `*.mp3` | 音频，以 HCA 码率的 2 倍编码，带有精确的样本数和循环点；见下文的[问题](#关于音频与视频的问题) |
| `*.mp4` | [视频](spec/video.zh-CN.md)，H.264 码率为源视频的 1.5 倍，音频为 AAC；见下文的[问题](#关于音频与视频的问题) |
| `*.png`、`*.webp` | 图片。`storage` 视图中同一张图有两种格式：PNG 是无损原图，WebP 体积更小，适合预览 |
| `*.bytes`、`*.txt` | 游戏中的文本或二进制资源（`TextAsset`），原样保存 |
| 其他 `*.json` | 文档的 `format` 字段写明了格式，每种格式在[规范](spec/README.zh-CN.md)中都有说明 |
| 其他文件 | 游戏资源中的其他文件，原样保存 |

## 关于音频与视频的问题

### 为什么音频只有 MP3，没有 WAV、FLAC 这样的无损格式？

不是做不到。游戏里的音频是 [HCA](https://www.criware.com/en/products/adx2.html) 格式，这是 CRI ADX 音频中间件的编码之一，和 MP3、AAC 一样属于有损压缩：游戏打包时就已经舍弃了一部分信息。导出器的 HCA 解码器与 [vgmstream](https://github.com/vgmstream/vgmstream) 逐采样一致，写出 WAV 并不难；但把有损音频解码成 WAV 或 FLAC，只是把这份已经有损的结果原样摊开，体积大了好几倍，却不会多出任何声音。

日服的音频资源包共有 5978 个，含 19279 条音频流，全部是 HCA，采样率全部是 44.1 kHz；歌曲多为 117 kb/s 立体声，语音多为 70 kb/s 单声道。作为对比，CD 规格的无损音频是 1411 kb/s。MP3 以 HCA 码率的 2 倍编码，再向上取到 MP3 的标准档位：歌曲 256 kb/s，语音 160 kb/s（[音频](spec/audio.zh-CN.md#4-容器)）。

取 64 段样本（歌曲、背景音乐、界面音效、剧情音频、语音），把 MP3 与用参考解码器解出的 HCA 采样逐一对照：

- **听感**：按 [ITU-R BS.1387](https://www.itu.int/rec/R-REC-BS.1387)（[PEAQ](https://en.wikipedia.org/wiki/Perceptual_Evaluation_of_Audio_Quality)）客观评测，客观差异等级（ODG）在基本模型下中位数 −0.02、最差 −0.45，在高级模型下（只计 3 秒以上的片段）中位数 −0.03、最差 −0.29。ODG 预测的是 [ITU-R BS.1116](https://www.itu.int/rec/R-REC-BS.1116) 主观听音测试的五级损伤刻度：0 听不出差别，−1 能听出、但不令人厌烦，−2 略令人厌烦，−3 令人厌烦，−4 非常令人厌烦。实践中常以 −0.5 为经验界线：高于它，一般认为与原件难以区分。64 段样本在两个模型下都高于 −0.5。作为参照，同一个文件和自己比较，基本模型约为 +0.2。
- **波形**：把两者逐采样相减，[信噪比](https://en.wikipedia.org/wiki/Signal-to-noise_ratio)（SNR）中位数为歌曲 28 dB、语音 43 dB。有损编码舍弃的是被[听觉掩蔽](https://en.wikipedia.org/wiki/Auditory_masking)、本来就听不到的成分，所以这个差值在波形分析里看得到，却不代表听感；被舍弃的也可能只是 HCA 自身留下的量化噪声。
- **体积**（以游戏里的 HCA 原件为 1）：MP3 约为 2.2 倍（语音约 2.3 倍），[FLAC](https://xiph.org/flac/) 约为 7 倍（语音约 5 倍），WAV 约为 12 倍（语音约 10 倍）。换成无损格式，要再多花 2 到 3 倍的空间，存下的仍是同一份 HCA 的解码结果。

原件就在游戏的资源里：从资源包里取出 .acb（和 .awb），用 vgmstream 解码成 WAV，或者在程序里用 `sekai-codec` 解码。两者都与 CRI 的参考解码器逐采样一致。如果是想好好听歌，更推荐去流媒体平台听官方正式发行的版本：它们来自制作方的母带，通常是完整版，码率更高，部分平台还提供无损音质，也能直接支持创作者。游戏里的歌曲是为客户端压缩过的游戏尺寸版本。

### 这些音频能用来训练模型或做声学分析吗？

不推荐。问题不在码率高低，而在于 MP3 是在有损的 HCA 之上又做了一次有损编码（[转码](https://en.wikipedia.org/wiki/Transcoding)）。用来收听，这一层损失听不出来；用于训练和分析，它会带来这些问题：

- **误差会叠加。** HCA 解码出的采样已经是一次有损编码的结果；MP3 编码器又按自己的心理声学模型和量化方式重新舍弃一遍，留下另一种编码器的痕迹：不同的量化噪声、不同的频带取舍，以及鼓点等瞬态附近的预回声。这种反复编码造成的累积损失称为[代际损失](https://en.wikipedia.org/wiki/Generation_loss)，只会增加，不会抵消。
- **听不出，不等于模型学不到。** PEAQ 这类客观评测衡量的是人耳能否察觉差别；声码器、语音合成、歌声转换、音源分离等模型学习的是信号本身的统计特征，可能把编码痕迹当作声音的一部分学进去，再在生成结果中复现出来。这种影响因模型和任务而异，没有通用的指标能够量化，也就无法事先保证无害。
- **时间对齐。** MP3 编码器会在开头加入延迟、在结尾补齐整帧。文件用 LAME 标签记录了这两个数，读取标签的解码器（如 ffmpeg）能还原出精确的样本数（[无缝播放](https://en.wikipedia.org/wiki/Gapless_playback)）；忽略标签的工具则会让整段音频推迟约 1057 个采样（约 24 毫秒），并在末尾多出一段静音，影响与台词文本、乐谱或口型的逐帧对齐。
- **来源混杂。** 如果数据集里既有原件解码的音频，又有转码后的音频，两者的编码差异本身就会成为模型能分辨的特征，干扰它真正要学的内容。

做训练或分析，请直接使用 HCA 原件：按上一个问题的方法解码为 16 位 PCM，再按需要存成 WAV 或 FLAC。这就是游戏里这段声音最完整的形式，不会再多一层损失。使用前也请确认相关素材的权利归属与使用条款。

### 为什么视频是 MP4（H.264）？游戏里原本是什么格式？

游戏里的视频装在 CRI 的 USM 容器里（属于 CRI [Sofdec2](https://www.criware.com/en/products/sofdec2.html) 视频中间件）：画面是 [MPEG-1](https://en.wikipedia.org/wiki/MPEG-1)，一个 1993 年定稿的视频标准；声音是 CRI 的 ADX 或 HCA。较长的视频在资源包里被切成多段 .usm 文件，按编号拼接起来才是完整的一个。从日服抽取的 13 个视频，画面全部是 MPEG-1，尺寸从 512×288 到 3952×2400。MPEG-1 的“约束参数”把常规画面限制在 768×576 以内；更大的画面超出了这个范围，但标准本身允许，CRI 的编码器也照样写出。

浏览器播放不了原件：网页的 `<video>` 既不认识 USM 容器，也不支持 MPEG-1，更没有 ADX、HCA 解码器，要在网页里播放就必须转换。[H.264](https://en.wikipedia.org/wiki/Advanced_Video_Coding)（AVC）放进 MP4 容器，是目前兼容性最广的组合：主流浏览器、手机、电视和剪辑软件都能直接打开，几乎所有设备都有硬件解码。文件把索引放在开头，可以边下边播；声音转成 AAC。更新的编码（AV1、VP9、HEVC）在同等画质下文件更小，但旧设备缺少硬件解码，编码也慢得多，HEVC 在部分浏览器里还不能播放。

### 转成 MP4，画质损失了多少？

有损失，但很小。MPEG-1 本身就是有损编码，再转成 H.264 又是一次有损编码。H.264 比 MPEG-1 晚了约十年，保存同样的画面需要的码率少得多。视频按其 MPEG-1 流码率的 1.5 倍编码，码率跟随源视频：低码率的小视频不会被放大成大文件，高码率的大尺寸画面也不会被压糊（[视频](spec/video.zh-CN.md)）。

在抽取的 13 个视频上，用 [VMAF](https://github.com/Netflix/vmaf) 把 MP4 与解码后的 MPEG-1 逐帧对照：中位数 97.4，最低 94.9（约 4K 的标题画面），最高 98.9。VMAF 是 0 到 100 分的感知画质指标，100 表示与参照完全相同。常用的经验是，93 分以上一般认为[与原片难以区分，或只有能察觉但不令人厌烦的失真](https://www.realnetworks.com/sites/default/files/vmaf_reproducibility_ieee.pdf)；两个版本相差约 6 分，才算[刚好能看出差别](https://streaminglearningcenter.com/codecs/finding-the-just-noticeable-difference-with-netflix-vmaf.html)。

保持不变的：分辨率（宽或高为奇数时补到偶数）、帧率和帧数（逐帧对应，不丢帧也不插帧），以及 [4:2:0 色度采样](https://en.wikipedia.org/wiki/Chroma_subsampling)（MPEG-1 本来就是 4:2:0）。视频里的声音转为 192 kb/s 的 AAC，和音频一样属于转码。

要原片，或者要逐帧分析、训练模型：从游戏资源包取出 .usm（多段的按编号拼接），用 [cridecoder](https://github.com/Team-Haruki/cridecoder) 等支持 CRI USM 的工具拆出 MPEG-1 视频流，VLC、mpv、ffmpeg 都能直接播放。理由和音频一样：转码后的文件适合观看，不适合当作原始数据。

### 复现这些测量

测量使用导出器发布的文件，以及使用者自行下载的资源包。

**音频**，对每段样本：

1. 从 ACB 或 AWB 文件中取出这段样本的 HCA 流，用 `vgmstream-cli -i`（不循环）解码为 WAV，作为参照。`tools/compare-audio` 可以核对 `sekai-codec` 给出相同的采样。
2. 用读取 LAME 标签的解码器（如 ffmpeg，或使用 mpg123 的 libsndfile）把发布的 MP3 解码为 WAV，其样本数与参照相同。
3. 用 [GstPEAQ](https://github.com/HSU-ANT/gstpeaq) 评分：基本模型为 `peaq <参照> <待测>`，高级模型为 `peaq --advanced <参照> <待测>`，高级模型只计 3 秒以上的片段。
4. 信噪比为 10·log₁₀(Σ 参照² / Σ (参照 − 待测)²)，对全部采样和声道求和。
5. 体积分别取 HCA 流、MP3、参照的 16 位 WAV，以及参照的 FLAC（`ffmpeg -i <参照> -c:a flac -compression_level 8`）。

**视频**，对每个视频：

1. 把视频的各段 .usm 按顺序拼接，拆出 MPEG-1 流，存为 `.m1v` 文件。帧率在 USM 文件头中，`sekai-codec` 的 `usm_streams` 示例会打印出来。
2. 把发布的 MP4 与该流按帧号配对评分：

```bash
ffmpeg -f mpegvideo -framerate <帧率> -i video.m1v -i video.mp4 -filter_complex \
  "[0:v]pad=ceil(iw/2)*2:ceil(ih/2)*2,settb=1/1000,setpts=N*40[r];[1:v]settb=1/1000,setpts=N*40[t];[t][r]libvmaf" \
  -an -f null -
```

`pad` 滤镜把参照补到与 MP4 相同的偶数尺寸，`setpts=N*40` 让两边的帧具有相同的时间，于是评分对比的是第 n 帧与第 n 帧。ffmpeg 需带 libvmaf 构建。
