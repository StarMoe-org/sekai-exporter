# 对象与资产：导出 Unity 内容的含义

[English](objects-and-assets.md)

本项目是一个**导出器**。它读取游戏的 Unity 文件，但读取本身并非目的；目的是将其中的内容转换为**资产**，即可由游戏以外的程序打开、播放、渲染或运行的文件。本文阐述二者的区别、这一区别如何决定本工具的构造、本仓库默认产出的内容，以及如何加入新的资产形式。

## 对象

一个 Unity 文件（AssetBundle，或随应用安装的 player data）是若干**序列化文件**的容器。每个序列化文件由一组**对象**组成。一个对象是某个 Unity 类的一个实例，以字节形式存储：

| 组成部分 | 含义 |
|---|---|
| path ID | 64 位整数，在所属文件内唯一标识该对象 |
| 类 | 引擎内置类（`Texture2D`、`Mesh`、`Transform`、`Material`、`AnimationClip` 等），或在 `MonoBehaviour` 的情形下，由游戏开发者编写的脚本类 |
| type tree | 该类的字段布局，包括字段名、类型、顺序与对齐方式。下发的资源包通常包含 type tree，随应用安装的 player data 通常不包含 |
| 数据 | 按上述布局存储的字段值 |

对象之间通过 **PPtr** 相互引用。PPtr 是一对 `(文件序号, path ID)`，其中文件序号指向所属文件本身，或指向该文件外部文件表中的一项。

对象是引擎的**存储形式**，其设计目标是使引擎在特定平台上快速加载，而非供其他程序使用：

- 游戏中呈现为一个整体的内容，在文件中分布于多个对象，由 PPtr 相连，且常常跨越多个资源包。
- 载荷保持平台编码：贴图为 GPU 压缩格式（ASTC、ETC、BC）；网格通道可能经过压缩；动画曲线以流式或密集块存储，绑定关系以变换路径的哈希值表示；音频采用中间件格式，作为普通字节块存储。
- 游戏脚本（`MonoBehaviour`）包含由游戏代码定义的任意字段。文件记录了对象所属的类及其字段名称，但不记录这些字段的含义。

**解包**是将字节还原为对象的过程：打开容器，读取序列化文件，依据 type tree 读出每个对象的字段，并解析 PPtr。其结果是一张对象图。对象图是精确的，但仍属于存储形式。

## 资产

**资产**是一个自足的成品，可由引擎以外的程序直接使用，例如一张图片、一个模型、一个音频文件、一份剧本文档或一份曲线文档。

资产与对象几乎不存在一一对应关系。一个模型是一个对象**闭包**：一个根预制体，以及从它出发可以到达、且该模型所需的全部对象。一张精灵图是某张贴图上的一个**区域**，其矩形存储于另一个对象中。一个音频对象可以包含数十个 **cue**，每个 cue 各自构成一个资产。部分资产还依赖游戏的**数据表**，而数据表不在任何资源包中。

**导出**是将对象闭包转换为资产的过程。其中的核心问题是一个资产究竟应当包含哪些内容，而这一问题的答案并不存在于文件之中。

## 示例：MySekai 的一件家具

以 MySekai（游戏中的建造玩法）的一件家具为例。在资源包中，它并非单一的对象，而是分布于以下各处：

- 每种配色变体各一个预制体，即由游戏对象与变换组成的树；
- 若干网格，其中部分带有蒙皮，每个网格包含多个材质；
- 使用游戏自有着色器的材质，携带游戏自定义的参数与关键字；
- GPU 压缩格式的贴图，其中部分为 sRGB，部分为线性色彩空间；
- 动画片段，以及一个带有事件的动画状态机，事件用于触发开门、开灯等动作；
- 用于特效的粒子系统；
- 游戏脚本组件，用于标记角色可坐下或执行动作的位置、家具占用的格子、碰撞体，以及家具在导航网格上形成的障碍；
- 游戏数据表中的记录，包括名称、分类与摆放时的音效。

现将它导出为 glTF，分别供三种程序使用：

| | 网页模型查看器 | Blender 等 3D 编辑器 | 复刻游戏的运行时 |
|---|---|---|---|
| 几何 | 一个变体，静态网格 | 全部变体，带骨架 | 全部变体，蒙皮与存储时完全一致 |
| 材质 | 近似为 PBR 或无光照材质，仅含底色贴图 | 近似为编辑器的着色节点 | 着色器名称、全部参数、全部关键字，以及每张贴图的色彩空间，使运行时移植的着色器获得相同的输入 |
| 动画 | 至多一段烘焙后的片段 | 烘焙到骨骼上的关键帧 | 原始曲线，以及状态机与其事件，因为状态机由运行时自行执行 |
| 特效 | 不需要 | 不需要 | 粒子系统的原始形式，供运行时自身的粒子模拟使用 |
| 交互 | 不需要 | 不需要 | 坐点与动作点、摆放格子、碰撞体与导航障碍，均位于运行时所用的坐标空间中 |
| 坐标 | 遵循 glTF 约定 | 遵循编辑器的导入约定 | 遵循 glTF 约定，并附带回到制作空间的精确变换，因为碰撞在该空间中计算 |

三个文件均可为合法的 glTF，但它们是三个不同的资产。此外，若要使第三个文件**可以使用**，仅有 glTF 并不充分：运行时还需要自身的着色器实现、粒子模拟、状态机执行器与摆放规则。资产只是契约的一方，另一方是消费它的运行时。

容器格式本身同样存在差异：有的使用者需要 FBX，有的需要 glTF，有的需要 USD。即使容器相同，内容也可能不同，例如骨架的组织方式、动画采用烘焙还是保留曲线、材质采用近似还是原样携带、贴图采用内嵌还是外部引用、每个变体单独成文件还是全部变体合于一个文件。

## 资产形式的定义者

**资产的形式由消费它的运行时定义。** 运行时决定资产必须包含什么、以何种布局组织，以及哪些内容可以省略。

- 若该运行时以复刻游戏为目标，则资产由游戏定义，因为运行时需要游戏的语义：着色器参数的作用、状态机的运行方式、脚本所采用的默认值。此时导出器必须忠实还原游戏的语义。
- 若该运行时是查看器或编辑器，则资产由该程序定义。资产应当包含该程序能够渲染、导入或播放的内容；游戏的语义仅在影响最终呈现时才需考虑。

开放标准（PNG、WebP、FLAC、glTF、JSON）定义容器及其规则，例如 glTF 的右手坐标系与自上而下的贴图行序，但不规定其中应当包含哪些内容。

因此，一种资产形式是一项决定：以**某种**方式解释**某一组**对象闭包，写成**某种**容器，供**某个**运行时使用。本仓库的每一种资产形式都以规范文档的形式记录，说明导出的内容、适用的用途，以及结果对该用途为何正确。

## 通用解包器与通用导出器

解包只有一份契约，即引擎的文件格式。由同一引擎版本构建的游戏以相同的方式存储对象，type tree 又使文件能够描述自身的布局。因此，一份实现即可服务于所有游戏，成熟的通用解包器由此存在。

导出的契约则建立在导出器与消费者的运行时之间，其数量与程序的数量相同。通用工具既不了解使用者的运行时，也不了解游戏的语义，其能力限于：

- 导出由引擎本身定义的内容，例如将贴图导出为图片、将网格导出为模型文件。即便如此，它也必须选定一种容器、一种坐标约定、一种对「一个模型」的划分方式，以及一种材质近似方式；这些选择适用于部分运行时，而不适用于另一部分；
- 将其余内容按字段原样转储。

另有一类工具从对象重建编辑器工程。这同样是一种资产形式，其运行时是引擎的编辑器。

因此，解包可以通用，导出则不能。需要为特定运行时获取资产的一方，必须编写适配该运行时的部分，而这一部分构成了工作的主体。

## 本仓库的默认产出

本仓库的资产形式默认服务于 **Moesekai** 网站及其运行的各个查看器，包括卡面与剧情图片、剧情剧本、音乐与语音、视频、3D 服装、Live2D 模型以及虚拟演唱会。每一种默认形式即为这些查看器所消费的形式，其规范文档中均有说明。

其他形式为可选项，各自由独立的 feature 启用。其中一种按复刻游戏的运行时所需的完整形式产出 MySekai 资产，即上表最右一栏所示的形式。

## 本项目定位为导出器的原因

本工具的使用者需要的是资产。解包是共同的基础，规模较小且极少变化，只需实现一次并逐值核对。代码的主体与正确性工作的主体均位于导出环节：组装闭包、解码载荷、施加语义，并按运行时期望的结构写出标准格式。

项目的构造围绕这一点展开：

```
字节 ──解包──▶ 对象图 ──转换──▶ 资产 ──视图──▶ 输出布局
              （精确、已索引、      （每种资产形式      （为特定使用者
               跨文件引用已解析）    对应一个转换器）    确定的路径与格式）
                    │                                        │
                    └──────── 目录：现有内容及其来源 ────────┘
```

- **解包**精确读出每一个对象，并将其类、名称与引用一并编入索引，范围覆盖一个版本的全部文件。
- **转换**由一组转换器完成。每个转换器声明其接收的根对象类型、读取的游戏数据表与产出的资产形式，并指向该形式的规范文档。
- **视图**将已转换的资产组织为特定使用者所期望的目录结构与文件格式。同一批资产可以同时产出多个视图。
- **对象文档**同样始终可得，以 JSON 形式给出每个对象的字段，且引用已解析。批量运行随每个资源包写出对象文档，服务端也可以按请求生成。尚无转换器支持的内容均可在对象文档中无损获取。
- **目录**记录版本、资源包、对象、资产与文件，使用者可据此浏览输出；仅发生变化的资产会被重建。

## 加入新的资产形式

若使用者的运行时需要本仓库尚未提供的形式，欢迎贡献。本项目的架构使新增一种形式成为局部的小规模改动：

1. **从对象文档入手。** 导出相关的资源包，阅读对象文档，确定目标资产由哪些对象构成。
2. **先编写规范**，说明该形式面向的运行时、资产包含的内容、所依赖的对象与数据表、采用的容器，以及结果对该运行时为何正确。
3. **新增一个转换器**，作为独立模块，由其自身的 feature 启用。转换器接收一个根对象与一个上下文（用于获取被引用的对象与游戏数据表），并返回资产。转换器不读取文件、不决定输出路径、不写入目录，这些职责由框架承担。
4. **复用已有的转换器。** 面向新运行时的形式，往往等同于某个已有转换器在材质、动画或坐标上作出不同的选择。
5. **使用合成数据测试。** 测试与样例中不得包含游戏数据，输入须自行构造（参见贡献指南）。
6. **若仅需改变已有资产的组织方式**，应新增视图，而非转换器。

未编译进构建的转换器，会在其本应产出的每一个资产上以名称报告。关闭某个 feature 不会导致输出被静默丢弃。

流程与检查要求参见 [CONTRIBUTING.zh-CN.md](../CONTRIBUTING.zh-CN.md)。
