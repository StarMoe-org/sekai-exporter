# 视频

`video` 形式把 CRI USM 文件转换为浏览器与播放器可以播放的 MP4 视频。转换器：`sekai-convert` 中的 `video`（feature `video`）。形式版本：1。

## 1. 运行时

播放游戏影片的网页与媒体播放器。

## 2. 内容

一个成员：

| 角色 | 内容 |
|---|---|
| `video` | 视频流、USM 头中的帧率与画面尺寸，以及文件带有的音轨 |

## 3. 来源

根对象是容器路径以 `.usm.bytes` 结尾的 `TextAsset`。一个文件可以分成多段，存放在同一个包内，容器路径为 `<base>-001.usm.bytes`、`<base>-002.usm.bytes` 等。编号 001 的段是根；所有段的字节按编号顺序拼接，结果即 USM 文件。每一段都列在资产的 `sources` 中。

ADX 音轨可能在其头部声明的采样数之前结束，此时解码它实际包含的完整帧。

| 情形 | 结果 |
|---|---|
| 1 到最大编号之间缺少某一段 | 错误 `missing_segment` |
| 文件不是恰好一条视频流，或该流不是 MPEG-1 | 错误 `unsupported` |
| 第一帧不以 MPEG-1 序列头开始（例如流被加密） | 错误 `unsupported` |
| 文件有多条音轨，音轨既不是 ADX 也不是 HCA，或 HCA 音轨被加密 | 错误 `unsupported` |
| 文件损坏 | 错误 `malformed` 或 `truncated` |
| 找不到 `ffmpeg` 程序 | 错误 `encoder_unavailable` |
| 视频流不含任何画面 | 错误 `encode_failed` |
| `ffmpeg` 程序执行失败 | 错误 `encode_failed` |

## 4. 容器

成员是索引位于文件开头的 MP4 文件，由 `mp4-h264-aac` 编码器（版本 6）通过 `ffmpeg` 程序写出，该程序须已安装并带有 `libx264`。可用环境变量 `SEKAI_FFMPEG` 指定程序。

| 流 | 参数 |
|---|---|
| 视频 | `libx264` 编码的 H.264：preset `veryfast`，码率为 MPEG-1 流码率（其大小 × 8 × 帧率 / 其画面数）的 1.5 倍、GOP 12、最多 2 个 B 帧、`yuv420p`、2 个按条带划分的线程，每个输入帧对应一个输出帧。宽或高为奇数的画面补齐为偶数 |
| 音频 | FFmpeg 编码器输出的 AAC，192 kb/s，采样率与声道数同音轨 |

**码率。** MPEG-1 流本身已是有损编码，再编码一次会叠加第二种编码的误差。H.264 用比 MPEG-1 更少的比特保存同样的画面，因此码率取来源的 1.5 倍时，第二次损失很小。码率跟随来源，因此低码率的流不会变成很大的文件，高码率的大尺寸画面也能保住细节。要逐帧分析画面、或用画面训练模型的程序，应当从 USM 文件中取出 MPEG-1 流。

**颜色。** MPEG-1 以有限范围的 BT.601 YCbCr 保存画面，游戏客户端也按该范围以 BT.601 矩阵转换为 RGB。客户端在 gamma 空间渲染，RGB 值原样显示在屏幕上，因此它们是给 sRGB 屏幕的值。MPEG-1 流本身不声明这些；H.264 画面保留来源的 YCbCr 值，由视频流（其 VUI）与容器（类型为 `nclx` 的 `colr` box）声明：原色 BT.709（1）、传递特性 sRGB，即 IEC 61966-2-1（13）、矩阵系数 BT.601，即 SMPTE 170M（6）、有限范围。遵循这些声明的解码器显示的颜色与游戏相同。

容器不含其他元数据。相同的输入与相同的 FFmpeg 构建产生相同的字节。线程数固定，因为 `libx264` 的输出依赖于它；各线程编码同一帧的不同条带，因此输出不受线程调度时机影响，同时运行其他任务时也一样。

## 5. 正确性

USM 文件的流分离已与独立的 USM 分离工具逐字节比对。MP4 文件的帧数与时长用 `ffprobe` 与 USM 头比对。颜色声明用 `ffprobe` 从容器读回，并用 `trace_headers` bitstream filter 从视频流读回；编码结果解码出的画面在有无颜色声明时相同。
