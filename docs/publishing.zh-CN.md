# 发布

[English](publishing.md)

发布为[派生图](architecture.zh-CN.md)的结果赋予名称，并将其放置于使用者读取的位置。核心产出以内容寻址的结果；结果如何组织、存放于何处，属于一个独立且可替换的层。

## 单一 store

系统中只有一个 **store**：以内容寻址存放字节之处，可以是本地目录，也可以是 S3 兼容存储中的一个前缀。结果只写入一次。

- store 中的对象以 `<aa>/<sha256>.<扩展名>` 命名。与 Git 仓库中的对象相同，这一名称不承载含义；含义由指向该对象的索引与资产文档承载。
- store 的本地副本是一个容量有限的缓存。增量判断、缓存命中与发布差异只需要哈希，而哈希保存在目录中。只有当某个视图须产出不同的字节，或首次向一个新目标发布时，才需要再次读取字节。

## 语义随输出发布

- **资产文档。** 每个资产随附一份文档 `<逻辑路径>.asset.json`，该文档本身也是 store 中的对象。文档记录[资产形式及其版本](spec/asset-documents.zh-CN.md)、以 `(资源包, path ID, 类)` 表示的来源对象（资源包含多个序列化文件时另写序列化文件）、成员文件及每个文件的角色（例如某个材质的底色贴图，或某个音频对象的第三个 cue），以及该资产所引用的其他资产。
- **索引条目携带语义。** 索引分片的每个条目给出文件的名称、哈希、大小、媒体类型、所属资产及其角色，而不仅是名称与哈希。
- **对象文档**（`<资源包>/_objects.json`）给出每个对象的类、字段与已解析的引用。它们由 `objects` 子命令写出，输入目录中直接包含的每个资源包文件对应 `<输出目录>/<资源包>/_objects.json`。`update` 与 `export` 不写出它们。

因此，任何持有 store、索引与资产文档的人，都能查明每个文件是什么、来自何处，以及它与其他文件的关系。目录是这些信息的索引，可由其重建。

发布文档的格式见[发布文档](spec/publication.zh-CN.md)。

## 布局

| 布局 | 形状 | 重复 | 使用者的读取方式 |
|---|---|---|---|
| `paths` | store 本身，加上每个区服、每个视图的一份[路径索引](spec/path-index.zh-CN.md)：按字节序排列的路径分块，记录每个文件的哈希、大小与类型 | 无 | 通过解析器（例如 `sekai-exporter serve`，见[服务](serving.zh-CN.md)）把路径映射到对象 |
| `index` | `paths` 布局，加上按目录划分的小型 JSON 分片（将每个名称映射到其哈希、大小、类型、所属资产与角色），以及一个索引根，其目录、列表与失败项都是切成分块的表 | 无 | 先查索引，再取对象。Rust 工作区之外提供一个带缓存的小型 TypeScript 解析函数 |
| `tree` | 每个区服、每个视图一棵路径树 | 后端不支持链接时，出现在多个区服中的字节在每棵树中各存一份 | 按路径读取 |

`paths` 与 `index` 布局直接引用 store，不复制任何内容。`tree` 布局在本地文件系统及支持链接的后端上使用硬链接，在普通 S3 上使用服务端复制。

每种资产形式另有一份**列表**，给出某区服某版本中该形式全部资产的逻辑路径、资产形式、指纹与大小。使用者以列表取代为单个查看器专门构建的索引。

## storage 视图

`storage` 视图还原 Moesekai 网站及其他读取方所使用的资源存储站的路径树，路径、文件名与编码参数均保持一致。共享同一逻辑路径的资产使用[架构](architecture.zh-CN.md)中定义的名称。它与 canonical 视图一样发布，在 `<区服>/storage` 下有路径索引和指针，因此[解析器](serving.zh-CN.md)能在固定路径上提供它，并让所有路径同时切换到新版本。

`tree`（例如 `export --tree` 写出的路径树）无法原子切换，因此按以下顺序写入：

1. 写入全部新文件；
2. 写入新版本的列表；
3. 新版本不再包含的文件，延后一个发布周期删除，使读取上一版本的读者得以完成读取。

由此得到的一致性有如下界限：每个文件的替换是原子的；在写入一个版本期间，读者可能同时看到上一版本与新版本的文件；中断后再次运行发布，结果收敛到新版本；资产存在错误的文件保留其原有字节，直至转换成功。

## client 视图

`client` 视图包含客户端安装包的资产，即客户端从安装包加载、不经下载的资产：player data 中的图片、字体，以及剧情在场景之间显示的界面预制体；streaming assets 中的 cue sheet，例如菜单音效与标题画面音乐，以及它附带的 Unity 资源包，例如字体和预先附带、免于下载的下载资源包。`update --client` 以规范布局发布它，指针位于 `<region>/client`，版本取[安装包](sources.zh-CN.md#区服配置)给出的版本；其状态保存在 `<region>-client` 下，与该区服资产的状态分开。

## 发布协议

1. 只有在本次运行没有运行失败（下载失败、写入失败或进程崩溃）时，版本才会被发布。资产错误不妨碍发布，并随版本一并列出。
2. 索引分片不可变，以其 SHA-256 命名。
3. 一次发布的修订号由其路径索引与失败项的分块得出，分块只取决于其中的内容。一次发布可以写成对上一次发布的改动，只读写改动落入的分片与分块，得到的文档与整份写出相同。
4. 推进某个版本的指针之前，核验该发布所引用的每个对象均以其所记录的哈希存在于 store 中。对象先以临时名称写入再改名，因此以名称存在的对象是完整的。
5. 指针先写入 `<区服>/<视图>/versions/<发布版本>.json`，再在 `<区服>/<视图>/current.json` 设为当前，因此只要对象仍保留，每个已发布的版本都可访问。指针还指明视图的[版本历史](spec/version-history.zh-CN.md)以及本版本相对上一版本的改动，因此读取方无需列出 store 即可列出已发布的版本。发布版本的名称由 ASCII 字母、数字、`.`、`_` 和 `-` 组成，且不全是点。
6. 失败以失败阶段的名称报告。失败的阶段不改变原有指针。
7. 一次发布面向多个目标时，各目标的指针并非原子地一同推进。每个目标保留其最近一次完整的指针，再次运行发布即可补齐其余目标。

## S3 兼容存储桶

启用 `s3` feature 时，若配置文件有 `publish.s3` 一节，`sekai-exporter update` 还会把产物发布到 S3 兼容的存储桶：

```json
{
  "regions": { "...": {} },
  "publish": {
    "s3": {
      "endpoint": "https://s3.example.invalid/bucket",
      "region": "us-east-1",
      "prefix": "sekai/",
      "layout": "index",
      "connections": 8,
      "secrets": { "access_key_id": "SEKAI_S3_ACCESS_KEY_ID", "secret_access_key": "SEKAI_S3_SECRET_ACCESS_KEY" }
    }
  }
}
```

| 键 | 值 |
|---|---|
| `endpoint` | 存储桶地址，路径式（`https://<主机>/<存储桶>`）或虚拟主机式（`https://<存储桶>.<主机>`） |
| `region` | 请求签名所用的区域 |
| `prefix` | 可选。加在每个对象名前面；为空或以 `/` 结尾 |
| `layout` | 可选。canonical 视图的[布局](#布局)：`"index"`，即默认值。storage 视图总是以 `paths` 布局上传 |
| `connections` | 可选，默认 8。同时进行的请求数，也是请求之间保持打开的连接数 |
| `listings` | 可选，默认与 `connections` 相同。同时进行的列表请求（`ListObjectsV2`）数，用于同时应答大量列表请求时比其他请求慢的服务 |
| `secrets` | 存放访问密钥 ID 和私有访问密钥的密钥名。每个值从同名环境变量读取，或从 `--secrets` 目录中的同名文件读取 |

存储桶的结构与本地输出相同：store 的每个对象位于 `<prefix>store/<aa>/<sha256>.<extension>`，canonical 与 storage 视图的指针位于 `<prefix>published/<区服>/<视图>/current.json` 和 `<prefix>published/<区服>/<视图>/versions/<发布版本>.json`。`store/` 下的不可变对象附带 `Cache-Control: public, max-age=31536000, immutable`，指针附带 `Cache-Control: no-cache`。请求用 AWS Signature Version 4 签名，密钥需要在该前缀下读、列出和写对象的权限。

一次运行从它读到的记录、之前运行的[上传日志](#上传日志)和存储桶接受的上传得知存储桶持有哪些对象，不逐个对象询问存储桶。它上传版本中在本地 store 里、且未知已被持有的每个对象。既不在本地 store、也未知已被持有的对象视为在存储桶中，因为每个对象都先于任何指向它的记录或指针放入存储桶。一次运行第一次查找记录时，列出全部记录包并整批读入。`update --verify` 先列出整个 store（`ListObjectsV2`，每个连接列其 256 个目录之一），上传版本中存储桶缺少的每个对象；存储桶持有的版本对象大小不符，或缺少一个本地 store 也没有的对象时，以 `verify` 阶段停止；并且在版本未变时也会运行。同一次 `update` 的各区服共享对存储桶的了解，因此 `--verify` 只为所有区服列一次 store，一个区服上传的对象，其后的区服也已知道。每次上传都用字节的 SHA-256 签名，这也是对象的名字，因此存储桶不会存下不匹配的字节。所有对象都在存储桶里之后才写指针，且只在指针改变时写。失败时发布停止并报告失败的阶段名，旧指针保持不变；再运行一次只上传仍缺少的部分，也只重新转换派生未被记录的资产。

## 区服的状态

`update` 在站点保存每个区服的状态：有存储桶时在 `<prefix>state/` 下，没有时在 `<输出目录>/state` 下。一次运行只读取这份状态和视图的指针，因此 `<输出目录>` 为空的机器也能从上次运行停下的地方继续。

同一时间只有一次运行写存储桶的状态和指针。`update` 的一次运行、`update --watch` 的每次更新以及 `gc` 在运行期间持有站点租约：状态文件 `lease.json`，记录操作、主机和取得租约的时间。运行以“桶里没有该文件时才写”（`If-None-Match: *`）取得租约，每两分钟以“仍是自己上次写入的实体标签时才写”（`If-Match`）续约，结束时以同样的条件删除；删除失败时租约留待过期，运行的结果照常有效。发现租约被占用的运行会等待，每 30 秒再看一次，并打印持有者。十分钟未续约的租约（按存储桶给出的 `Date` 与 `Last-Modified` 判断）以针对该文件的 `If-Match` 接管。租约被接管的运行不再写状态或指针；它已上传的对象留在存储里，下一次运行会用到。存储桶需要支持条件写入。重试能改变结果的失败请求（连接断开、回复被截断、408、429、499 或 5xx）会再次发送，间隔从一秒起逐次加倍、最多一分钟，持续一个租约的时长，因此运行能撑过存储桶的短暂中断。

| 文件 | 内容 |
|---|---|
| `versions/<区服>.json` | 上一个版本的标识，以及在 `evaluation` 下按部分（`unit`、`form <名称>`、`table <名称>`）记录的、产生其资产的评估身份。`update` 与 `update --check` 与它比较；没有 `evaluation` 的记录视为以不同方式评估 |
| `regions/<区服>.json` | 区服状态的根，列出它的分块 |
| `chunks/<aa>/<sha256>.json.gz` | 所有区服状态的分块：上一个版本的资源包及其内容和所含文件、各单元及其键、资产声明的名称及各名称归属的单元、由数据表构建的资产及其各自的读取，以及各视图发布的修订号 |
| `records/packs/<sha256>.json.gz` | 记录包，各区服的记录都写在这里：一个单元给出的结果，以其资源包内容与求值设置构成的键存放，任何区服中键相同的单元都可取用；以及一次派生得到的对象及其大小 |
| `uploads/<sha256>.txt.gz` | [上传日志](#上传日志)：未完成的运行已上传到存储桶的对象 |

记录包是 gzip 压缩的 JSON 行：先是头部 `{"format":"record-pack","version":1}`，之后每行一条记录，`{"unit":"<键>","record":<单元记录>}` 或 `{"derivation":"<指纹>","record":<派生记录>}`，键和指纹都是小写十六进制。派生记录是 `{"document":{"key":"<sha256>.<扩展名>","size":<字节数>}}`；根中没有该形式的资产时为 `"nothing"`。单元记录在前，派生记录在后，各按键排序，同一对象只有一条记录；头部之后的各行合计不超过 8 MiB，除非单条记录本身更大。相同的记录总是给出相同的字节，记录包写入后不再改动。多个记录包都有同一对象的记录时，运行取名字排在最前的那个包里的记录。

单元记录列出单元的每个资产及其根的逻辑路径与 `root`：根为对象的资产是 `{"path_id": <path ID>}`，资源包含多个序列化文件时在 path ID 之前另有 `"file": "<序列化文件>"`；根为资源包中非序列化文件的资产则为 `{"file": "<路径>"}`；每个未命名的根是其逻辑路径与同样取值组成的一对。

状态切分为内容寻址的分块，因此一次运行只写其改动落入的分块。一次运行在求值的同时上传每个资产的产出，即资产文档及其指明的成员，待它们都已在站点后记录该派生。记录攒满一个包，或距上一个包已过五分钟时，写成一个记录包，因此中途停止的运行会把已写入包中的派生留给下一次运行。随后它依次写入其余新对象（例如视图的对象）、带有单元记录的最后一个包、状态，最后写指针。记录只在其指向的对象都已在站点后才写入。若状态中的修订号与当前指针的不一致，本次运行整体发布两个视图，只保留状态中的资源包。

### 上传日志

向存储桶发布的运行把存储桶确认的上传写进日志：版本的所有对象都已在存储桶时写一次，上传期间距上一个日志文件五分钟时写一次，未完成就停止时也写一次。日志文件是 gzip 压缩的文本：头部一行 `upload-journal 1`，之后每行一个对象，`<sha256>.<扩展名> <大小>`；文件以其字节的 SHA-256 命名。一次运行中第一个有工作的区服列出 `uploads/`，读入所有日志文件，把其中列出的对象视为已持有；`--verify` 列出整个 store 时则不读。因此在本地 store 仍保有这些对象的机器上，中断之后的那次运行不会再上传被中断的运行已放进存储桶的对象。一次运行把它更新的所有区服都带到当前版本后，删除它读入和写下的日志文件；未完成的运行则把这些文件连同自己的一起留给下一次运行。

内容与评估都相同的版本，在其某个视图的指针指明更早格式的文档（版本低于当前版本的索引根、分片与分块，见[发布文档](spec/publication.zh-CN.md#6-版本)）时会再次发布。格式更早、但指明当前格式文档的指针保留到下一个版本，下一个版本作为对它的改动写出。

## 回收垃圾

一次运行只添加对象和状态文件，从不删除：不再被任何发布引用的对象、早先状态的分块、早先评估的记录都会留在站点上。`sekai-exporter gc <输出目录> [--config <文件>]` 找出这些文件（有配置时在配置的存储桶中，否则在 `<输出目录>` 中），加 `--delete` 时删除它们。

| 保留 | 原因 |
|---|---|
| `published/` 下的每个指针 | 每个指针都指明一个已发布的版本，无论是否为当前版本 |
| 每个指针引用的每个对象 | 它的索引根、表分块与分片，路径索引的根与分块，目录树、版本历史与变更，以及路径索引列出的每个文件 |
| 每个区服状态的根、根指明的分块，以及该区服由数据表构建的资产文档及其成员 | 一次运行会保留由数据表构建的资产而不重新写出 |
| 所指对象全部保留的记录 | 一次运行认为记录所指的对象都在站点上 |
| 宽限期（`--grace`，默认 `1d`）内写入的文件，以及其中的记录所指的对象 | 正在发布的运行先写对象和记录，最后才写指针 |

其余的 store 对象、状态分块和记录都是垃圾；[上传日志](#上传日志)的每个文件也是垃圾，因为它列出的对象可能被删除。记录包中的记录从不改动，因此宽限期之前写入的记录包，若含有不再保留的记录，或其中的记录不足 2 MiB，`gc` 就重写它：把所有这类包中仍保留的记录写进新的记录包，并报告新包的数量与大小。新包与某个原包完全相同时，原包保留。逐个文件存放的记录（`records/units/<aa>/<键>.json` 和 `records/derivations/<aa>/<指纹>.json`）也以同样方式并入记录包。`gc` 按类别（上传日志、记录包、单文件单元记录、单文件派生记录、状态分块、对象，对象另按扩展名）列出垃圾的数量与大小，不加 `--delete` 时不写入也不删除任何文件。加 `--delete` 时先写入新包，再删除日志文件和被新包取代的记录文件，然后删除状态分块和对象，因此中途中断的回收既不会丢失仍保留的记录，也不会留下指向已删除对象的记录。若某次运行取用了这样的记录，就会发布一个指向站点缺失对象的指针，因此 `gc` 只在站点上没有 update 运行时执行。在存储桶中，`gc` 读取列表给出的时间（`LastModified`），`--delete` 需要删除前缀下对象的权限。

无论站点在哪里，`gc` 也回收运行留在 `<输出目录>` 本身中的文件。[输入 store](sources.zh-CN.md#输入-store) 中的资源包，若按 `<输出目录>` 的 catalog 记录，没有任何区服最近一次取得的是它，就是垃圾；输入 store 或 store 的 `incoming/` 中的文件，是中断的运行未写完的文件。两者在宽限期之前写入的都是垃圾，`--delete` 在删除站点的文件之后删除它们。catalog 不存在、没有记录任何取得，或无法读取时，输入 store 中的资源包都不算垃圾。之后的运行再次需要某个资源包时会重新下载。

指针从不删除，因此每个已发布的版本都保持可达。同名版本再次发布时会替换该版本的指针，只有早先那次发布引用的对象随之成为垃圾。

## 求值与发布的组合

| 部署形态 | 求值 | 地点 | 布局 |
|---|---|---|---|
| 完整的静态镜像 | 急切 | 批处理 | `index`，路径由[解析器](serving.zh-CN.md)提供 |
| 存储有限的自托管 | 绑定急切，转换惰性 | 服务：以库的形式使用各 crate 的程序，因为 `serve` 只解析已发布的文件 | `index`，store 作为可淘汰的缓存 |
| 无服务器 | 绑定急切，转换惰性 | 运行 WebAssembly 核心的函数：查找绑定、获取资源包、转换、缓存、返回 | `index` |
| 只持有自有文件的使用者 | 惰性 | 浏览器：WebAssembly 核心在本地解包并转换拖入的资源包，无需服务器 | 无 |
| 其他程序 | 任意 | 库 | 由该程序决定 |
