# Pipeline

[中文](pipeline.zh-CN.md)

The pipeline evaluates the [derivation graph](architecture.md) bundle by bundle, with the streaming evaluator described below. One run processes the current version of the region it names on the command line, in a single process, with one catalog and one record of derivations.

## Stages

| Stage | Work | Output |
|---|---|---|
| P0 Plan | Read the [asset identity and table identity](sources.md#version-identity) of each region, and the identity of the evaluation: the revision of units, the class layouts, and the identity of each converter and table converter | Nothing to do if all three match the last complete run. When the asset or table identity changed, the manifest is read again; bundles whose declared hash is unchanged keep their stored bytes and their index. When only the evaluation changed, the run evaluates the units whose results it no longer holds for, such as those with roots of a converter of a new version |
| P1 Manifest | Download and parse the manifest; select bundles by name, with their dependencies | The bundle list with declared hashes, sizes and dependencies |
| P2 Fetch | Download each selected bundle, deobfuscate it and hash it while it streams, and write it to the store | Bundle inputs, identified by content hash |
| P3 Index | For each bundle, when the first unit that needs it opens it, read every object's fields, skipping large arrays by length; record class, name, container path, content hash and references. The index is stored by the content hash of the bundle and reused | Object rows and reference edges |
| P4 Plan units | For each bundle, in name order and in segments (see [Streaming evaluation](#streaming-evaluation)): resolve external files and `m_Script` within its window; each converter selects the root objects of the bundle and computes closures over the reference edges and the further inputs it declares, within the window, and a converter whose form also starts from files selects the root files among the entries of the bundle that are not serialized files; names are assigned from the bundle (see [Identity](architecture.md#identity)); fingerprints are computed | Derivations to evaluate; derivations whose fingerprint already has an output are reused without reading any bytes |
| P5 Convert | Evaluate the convert and transform derivations of a segment under the scheduler | Asset documents and file bytes |
| P6 Write | Write bytes to the store, skipping content that already exists; record derivations in the catalog | Store objects and catalog rows |
| P7 Tables | Build the assets of the [table stage](#table-stage) | Asset documents and file bytes |
| P8 Views | Each enabled view produces bindings; views that need other bytes produce transform derivations; the `index` layout is published | Bindings |
| P9 Commit | Verify that every bound object exists in the store, then advance the version pointer | A committed version, with its asset errors listed |

## Invariants

- **Increments follow object content, not bundles.** A bundle that is rebuilt without changing its objects leaves every object hash, and therefore every asset fingerprint, unchanged. P2 and P3 run only for bundles whose [declared hash](sources.md#declared-hashes-and-content-hashes) changed; the index of an unchanged bundle is reused.
- **Every object is accounted for.** `ledger.tsv` lists each bundle with the number of its objects that are roots, read by a conversion, of a class or script declared to carry no asset content, or unknown, and of its resource files read. A bundle's account is settled after the last unit whose window holds it, when no later conversion can read it. A bundle is complete when nothing is unknown and every resource file was read.
- **A conversion reads only its closure.** Reading any other object fails the asset with the error `undeclared_read`, so everything an output depends on is in its fingerprint.
- **Fingerprints contain everything that determines the content:** the converter name and version, the name of the asset, the hash of the class layouts when the source supplies them, the content hash of each object in the closure, and the content hash of the exact streamed `.resS`/`.resource` byte slice (`m_StreamData` / `m_Resource`) referenced by each object in the closure that streams external data. Sibling objects in the same bundle that do not read streamed data, or whose slice is unchanged, keep their fingerprints when the streamed data of another object changes. An encoder is part of the fingerprints only when its files lose information: the audio (MP3) and the video (MP4) encoder, for the forms that declare them (`Converter::encoders`). The lossless encoders are not: their files decode to the content they were given, whatever the version.
- **Content that was encoded keeps its file:** an encoding has a fingerprint of its own, made of the encoder and the decoded content, with the version of the encoder when it loses information. A conversion that runs again and decodes the same content reuses the file recorded for it and does not encode. Assets built from tables have the fingerprint described under [Table stage](#table-stage). Configuration does not change output paths, formats or encoder parameters; those are defined by converters and views.
- **Asset errors and run failures are different things.** An asset error is the result of evaluating an asset: a named error that is as deterministic as a successful output. It does not affect other assets, it does not stop the version from being committed, and it is listed with the version. Because it has no successful output, the next run evaluates it again. Missing members, such as a bundle that the asset list names but the source does not serve, are asset errors. A run failure is a failed download, a failed write or a crash. Only run failures stop a commit.
- **The order of work does not affect output.** Each output depends only on its inputs, and the catalog is written in key order at the end of each batch. Store contents and the catalog contents sorted by primary key are independent of thread count and scheduling.
- **A commit is all or nothing per version.** P9 advances the pointer only after verification. When verification fails, the stage that failed is reported by its fixed name and the previous pointer stays in place.

## Streaming evaluation

The streaming evaluator evaluates a version from its manifest, one bundle at a time. No step needs the whole version at once.

- **Units.** A unit is one bundle of the manifest with its window: the bundle and every bundle it depends on, directly or through others. The roots of a unit are the root objects of its bundle and its root files: entries that are not serialized files, such as the cue sheets a client package keeps as files, which a conversion reads alone. A root file is identified by its path in the bundle and the SHA-256 of its bytes. The roots are named from that bundle alone, and their closures, declared inputs and script references are followed only inside the window.
- **References outside the window.** A reference in the closure of a root to a file of a bundle outside the window makes the asset fail with the error `outside_dependencies`, whose message names the referring bundle and object and the external file. A script reference outside the window does not resolve. Every such reference is listed with the result. References to engine files that no bundle holds stay out of closures.
- **Dependencies.** A bundle depends on each bundle that holds a file its serialized files name as an external file. When several bundles hold a file of the same name, the first in name order holds it. A source whose manifest lists no dependencies, such as a directory, has them read from the bundles. A source whose manifest lists them has these added to what it lists, since a client also resolves external files among bundles it loaded without a listed dependency, such as shared shaders. Which files a bundle holds and names is kept in the catalog by the SHA-256 of its bytes, so an update reads only bundles that no earlier run has read.
- **Segments.** Units run in manifest order, in segments of consecutive units, bounded by a number of units and by the declared size of the bundles of their windows. The bundles of a segment are opened together and its derivations run under the scheduler. A bundle stays open, indexed and parsed until the last unit whose window holds it, which the manifest tells in advance. Parsed bundles are kept within an estimate of their memory, and stored indexes are kept in memory only while a later unit needs them.
- **Results.** Every closure stays inside its own window, so documents, member files, fingerprints, names and ledgers do not depend on how units are grouped into segments or on the number of threads. Assets of different bundles that receive the same name are left unnamed. Publishing follows the last unit.
- **Errors.** Bundles that cannot be read, opened or indexed, bundles that share a name, and dependencies that the manifest does not list are reported by bundle name. The units that need them still run, and references that reach them fail as described above.
- **Recorded units.** When the manifest identifies the content of every bundle of a window, the result of the unit is recorded under that content, the class layouts, the size limit of assets and the loose classes of the source, together with the forms whose roots the run looked for and the version of each converter the unit has roots of. A later run takes the recorded result without fetching the window while those versions are the same, so a new version of a converter evaluates again only the units that have roots of its form. For a form the result was not looked for in, the run reads the stored indexes of the bundles of the window and takes the result when the unit has no roots of that form; when an index is not stored, the unit is evaluated. A new form therefore evaluates again only the units that have its roots. Which objects are roots is fixed for a form name, whether or not its converter is compiled into the build. A unit is recorded only when no bundle of its window had an error. When an asset of a form failed to convert, the record also holds the revision of that converter, and a later run takes it only while the revision is the same. A converter that learns to read assets it failed needs a new revision rather than a new version: the units with failed assets of its form are evaluated again, and no other unit is.

## Table stage

Some assets, such as [episodes](features.md), have no root object: each is built from rows of the game data tables and from assets the version already holds. After the last unit, each table converter reads the tables it needs and lists its assets, and each asset is built.

- **Inputs.** A table converter sees the tables, the assets of each bundle with their forms, the document of an asset and the bytes of its members. It reads no object of a bundle. A converter first plans its assets from the tables; each asset is then built on its own, reading the version through a context that notes every read, and reading what its plan derived only through the plan's shared maps, by key.
- **References.** An asset that a row needs and the version does not hold is recorded in the asset being built. A run over a selection of bundles therefore gives assets that record what the selection left out.
- **Failures.** A table that cannot be read or parsed is a run failure. An asset that cannot be built is an asset error.
- **Reuse.** The state of a region keeps, for each asset of a plan whose assets read it only that way, what the asset read: the tables, the list of bundles, the assets of each bundle, the documents of assets and the entries of shared maps, with a digest of what they gave. A later `update` keeps the asset when its reads give what they gave, with the same form and version, and builds it again otherwise; `--rebuild-tables` builds every one again, which gives what an `update` from no state gives. A failure of the store is never kept.
- **Fingerprints.** No derivation is recorded for these assets. The fingerprint is the hash of the form and its version, the name, the role and content hash of each member, the references and any error, so it changes exactly when the output changes.

## Regions

Each region runs in a process of its own, named on the command line. The record of derivations keeps the fingerprint of each converted asset, and the fingerprint does not contain the region. A region converts an asset again in a later run only when its own record does not hold the output of its fingerprint, which is what reading the same objects gives. A bundle is reused from an earlier run when that run's output directories are listed in `stores` and the bundle has the same declared hash there.

Game data tables are read from the region's `tables` source. Table rows are not part of the record of derivations: an `update` keeps the assets of the table stage as [the table stage](#table-stage) says, and `export` builds them in every run.

## The client source

Assets inside the client package go through the same pipeline. `sekai-exporter export` reads an APK, or an XAPK that holds several APKs, when `--class-table` names a TPK file with the layouts of the engine classes. The files under `assets/bin/Data/`, or the entries of a UnityFS container among them, become one bundle named `player`. Files that the player data stores in parts are joined first. The cue sheets of the streaming assets become a bundle named `streamingassets`, and each Unity bundle among the streaming assets is a bundle under its own name, as the [sources](sources.md#region-configuration) describe.

Objects without type trees are read with the layout of their class at the Unity version their file states. A `MonoBehaviour` also needs the layout of its script: `--script-table` names a gzipped file with one JSON object per line, holding `assembly`, `class` and `nodes`, the fields of the script in preorder as `type`, `name`, `level`, `byteSize`, `typeFlags`, `version` and `metaFlag`, the top fields at level 1. The object is read with the engine header of its class followed by those fields. Without the table, or for a script that the table does not list, it is recorded with the error `no_layout`. Every object must be read exactly to its end; an object that is not read exactly is recorded with a named error.

`script-table` builds such a table for a client package. The layouts a script may have are the rows of other tables, given with `--script-table`, and the type trees that the bundles under each `--bundles` directory store for their `MonoBehaviour` objects. A stored tree is taken when it starts with the engine header of a `MonoBehaviour` at a Unity version of the package's files, and its nodes after the header are the fields. For each script whose objects the package stores without a type tree, every layout is tried on every one of those objects, after the engine header at the Unity version of the object's file, and the script is kept with the one layout that reads all of them exactly. A script for which no layout was found, none reads every object, or several do, is left out. The command prints each script with the number of its objects and what became of it: kept, with the table or bundle file its layout was found in, or left out with the reason, and for a script no layout reads, the first error of each layout.

The container of the `ResourceManager` object names assets as the container of an `AssetBundle` object does, with the load paths the game uses. The hashes of the tables are part of the fingerprint of every asset of the run.
