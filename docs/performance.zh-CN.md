# 性能

[English](performance.md)

性能是求值器的性质，而非转换器的性质。转换器是从对象视图与上下文到资产字节的纯函数。缓存、增量求值、共享、惰性求值、并行、融合编码与内存控制全部位于求值器中，任何转换器都不包含线程、缓存或输入输出。因此，各项优化集中于一处，编写转换器的贡献者无需了解这些优化，且每一项优化都可以单独关闭，与未启用时的求值结果对照。

维系这一结构的检查是：**优化求值与朴素求值产生相同的字节。** 朴素求值在单线程下运行，不读写派生记录，也不进行融合编码。合成资源包上的测试将它与多线程、分段、惰性以及有无有界块缓存的求值相比对；持续集成将 `wasm32` 构建写出的 store 与原生构建的逐字节比对。

## 考虑的次序

工作按以下次序削减，每一步都在考虑下一步之前完成。

| 步骤 | 方法 | 位置 |
|---|---|---|
| **避免工作** | 指纹已有输出的派生直接沿用；各区服之间按内容哈希共享下载、转换与存储；只求值被请求的绑定；将资源包的索引视为派生，资源包未变化时沿用；解码内容此前已编码过的，沿用其文件 | 求值器与 store |
| **少读** | 索引阶段只提取引用、名称与内容哈希，大数组（像素、顶点、音频块）按长度跳过；载荷在转换需要时才读取；外部流按字节区间读取 | `sekai-unity` |
| **少拷贝** | 解压后的块保存在受内存预算约束的缓存中，读取器从中借用切片；对象文档在读取对象的同时写出，不构建值树；转换器以值树读取对象，对于经测量表明值树开销较大的类，再加入直接在字节上读取的强类型读取器 | `sekai-unity` |
| **并行** | 单一调度器，见下文 | `sekai-pipeline` |

## 读取

**布局编译。** 一份 type tree 被编译为一段扁平的读取程序，其指令包括：读取定长值、跳过定长字节、对齐、遍历数组、读取 PPtr、读取字符串。文件打开时，其中每份 type tree 编译一次。索引所用的引用提取器、对象文档写出器与强类型读取器是同一段程序的不同解释，因此每种布局只有一份实现。不带 type tree 的对象所用的布局表编译为同一种程序。

**块缓存。** UnityFS 以 LZ4 或 LZMA 块存储数据。解压后的块以 `(资源包内容哈希, 块序号)` 为键缓存，缓存占用计入内存预算。读取一个对象时，只解压包含该对象的块；多个读取者同时未命中的块只解压一次。

**文件。** store 中的资源包按偏移从其文件读取，不移动游标，因此多个线程共用一个句柄。最近读取的文件在两次读取之间保持打开，数量有固定上限。

**资源包索引。** 资源包的索引及每个对象所读流或资源切片的摘要只取决于资源包的字节，因此以字节的 SHA-256 为键存放在目录中。打开版本时，已处理过的资源包直接读取存储的索引，只解析新的资源包。读取对象或资源时才解析对应的资源包，只有最近使用的资源包保持解析状态，多个读取者同时打开的资源包只解析一次。

## 调度

- 求值按分段流式遍历清单：每段是按名称排列的连续单元，每个单元是一个资源包及其依赖的资源包，段的大小受单元数与这些资源包声明的字节数限制。两段同时转换，同时打开并索引下一段的资源包；后续单元不再需要的资源包随即释放。
- 单一调度器运行于标准库线程之上，其任务是各段的派生与其资源包的索引。
- 调度器管理三种资源，每种以一个数值配置：CPU 槽位（默认为逻辑 CPU 数）、内存预算（默认为物理内存的一半），以及每个远端的并发连接数。除此之外没有其他线程池设置。
- 每个派生声明其开销等级与峰值内存估算，估算由对象头计算：贴图为存储的图像数据加上解码后大小的倍数，音频为 cue 表存储大小的倍数，其余为存储大小的倍数。剩余预算不足的任务等待，并允许其后有限个放得下的任务先行启动；超过整个预算的任务单独运行。
- 任务按其工作的各部分领取 CPU 槽位，并在把文件写入 store 之前归还。不存在其他线程池。
- 同一段内，读取相同资源包的任务归为一组。各组按组内最长任务从大到小启动，组内任务也从长到短，使一组读取的块留在缓存中，并缩短最后一批任务的等待时间。
- 网络传输与计算相互分离。下载在数据流入输入 store 对应目录中的临时文件的同时完成哈希计算与去混淆，再以硬链接落位。对同一主机的请求共用一条 HTTP/2 连接，此前运行已持有的资源包以链接复用而不重新下载。获取与求值同时进行，按求值打开资源包的次序获取，打开资源包时等待其到达，因此前面的段在后面的资源包仍在路上时就已开始转换。计算只从 store 读取。

## 热点

| 工作 | 方法 |
|---|---|
| 贴图解码（ASTC、ETC2、BC） | 每个任务解码一张图像；同一段的图像并行解码 |
| 图片编码 | **融合**：一个解码面在同一任务中编码为规范 PNG，有存储视图时再编码为有损 WebP，不重复解码，也不排队等待 |
| 音频 | HCA 逐帧解码并逐帧交给 MP3 编码器，任何流都不会整段以解码形式驻留；流与密钥相同的成员只编码一次 |
| 视频 | 每部影片由一个线程数固定的 `ffmpeg` 进程编码，视频流从其标准输入读入 |
| 编码 | 每次编码以编码器与解码后内容的指纹记录；转换再次解码出相同内容时，直接沿用已存储的文件，不再编码 |
| 对象文档 | 由编译后的读取程序直接写出 JSON，不构建值树 |
| store 写入 | 内容寻址，已存在的内容跳过；文件写在目标旁边再改名落位，本地 store 以硬链接物化路径树 |
| 发布 | 计划、索引、路径树与存储视图并行构建；检查每个成员是否在 store 中时，每个 store 目录只列一次，不逐个打开文件 |
| 目录 | 单个 redb 文件，写事务成批提交；读事务读取快照，不等待写入 |

融合编码不改变指纹：每项输出与不融合时的字节相同，融合与朴素求值的结果由测试比对。

## 度量

- 每个派生在目录中记录其墙钟时间、CPU 时间、读写字节数、估算的峰值内存，以及其成员解码后的大小。派生的开销为最近一次的测量值。`sekai-exporter stats` 列出开销最大的派生类型，以及内存估算与解码后大小相差最远的转换器。估算还包含工作副本和编码进程，因此有一定差距是正常的。优化以这份记录为起点。
- 每次运行在输出旁写一份 `metrics.jsonl`（每行一个 JSON 文档），并在运行时显示状态行：每秒采样一次的进程、其子进程与整机的 CPU、内存占用，以及每个阶段和派生的 span，含墙钟时间、CPU 时间与读写字节。求值器通过 `Recorder` 上报，自身不读时钟，因此度量不会影响任何产物。
- 基于真实游戏数据的基准测试由持有数据的一方在本地运行，其结果不属于本仓库的内容。
