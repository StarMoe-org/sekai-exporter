# 性能

[English](performance.md)

性能是求值器的性质，而非转换器的性质。转换器是从对象视图与上下文到资产字节的纯函数。缓存、增量求值、共享、惰性求值、并行、融合编码与内存控制全部位于求值器中，任何转换器都不包含线程、缓存或输入输出。因此，各项优化集中于一处，编写转换器的贡献者无需了解这些优化，且每一项优化都可以单独关闭，与未启用时的求值结果对照。

维系这一结构的检查是：**优化求值与朴素求值产生相同的字节。** 朴素求值在单线程下运行，不使用派生缓存，也不进行融合编码。持续集成比对单线程与多线程、有界块缓存与无缓存的结果。优化求值与朴素求值、原生构建与 `wasm32` 的比对，计划在求值器与转换器实现后加入。

## 考虑的次序

工作按以下次序削减，每一步都在考虑下一步之前完成。

| 步骤 | 方法 | 位置 |
|---|---|---|
| **避免工作** | 指纹已有输出的派生直接沿用；各区服之间按内容哈希共享下载、转换与存储；只求值被请求的绑定；将资源包的索引视为派生，资源包未变化时沿用 | 求值器与 store |
| **少读** | 索引阶段只提取引用、名称与内容哈希，大数组（像素、顶点、音频块）按长度跳过；载荷在转换需要时才读取；外部流按字节区间读取 | `sekai-unity` |
| **少拷贝** | 解压后的块保存在受内存预算约束的缓存中，读取器从中借用切片；常用类有直接在字节上读取的强类型读取器；通用值树仅用于对象文档 | `sekai-unity` |
| **并行** | 单一调度器，见下文 | `sekai-pipeline` |

## 读取

**布局编译。** 一份 type tree 被编译为一段扁平的读取程序，其指令包括：读取定长值、跳过定长字节、对齐、遍历数组、读取 PPtr、读取字符串。文件打开时，其中每份 type tree 编译一次。索引所用的引用提取器、对象文档写出器与强类型读取器是同一段程序的不同解释，因此每种布局只有一份实现。不带 type tree 的对象所用的布局表编译为同一种程序。

**块缓存。** UnityFS 以 LZ4 或 LZMA 块存储数据。解压后的块以 `(资源包内容哈希, 块序号)` 为键缓存，缓存占用计入内存预算。读取一个对象时，只解压包含该对象的块。

## 调度

- 单一调度器运行于标准库线程之上，其任务即派生图中的节点。
- 调度器管理三种资源，每种以一个数值配置：CPU 槽位（默认为逻辑 CPU 数）、内存预算（默认为物理内存的一半），以及每个远端的并发连接数。除此之外没有其他线程池设置。
- 每个派生声明其开销等级与峰值内存估算。估算由对象头计算：贴图为宽 × 高 × 4，音频为采样数 × 声道数 × 4，其余为载荷长度的倍数。剩余预算不足的任务等待；超过整个预算的任务单独运行。
- 可在内部拆分的任务，例如大贴图解码或长音频编码，拆分为子任务后交回同一调度器。不存在其他线程池。
- 任务按拓扑序运行，同一层内按估算耗时从大到小运行，以缩短最后一批任务的等待时间。
- 网络传输与计算相互分离。下载在数据流入的同时完成哈希计算与去混淆，并直接写入 store，不经临时文件。计算只从 store 读取。

## 热点

| 工作 | 方法 |
|---|---|
| 贴图解码（ASTC、ETC2、BC） | 按图像块并行，内层循环使用可移植的 SIMD |
| 图片编码 | **融合**：一个解码面在同一任务中编码为本次运行所需的全部格式（规范层的无损图片与视图所需的格式），不重复解码，也不排队等待 |
| 音频 | HCA 只解码一次，采样数据交给本次运行所需的每一个编码器 |
| 视频 | VP9 码流直接写入 MP4，不重新编码 |
| 对象文档 | 由编译后的读取程序直接写出 JSON，不构建值树 |
| store 写入 | 内容寻址，已存在的内容跳过；本地 store 以硬链接物化路径树 |
| 目录 | SQLite 采用 WAL 模式与批量事务；只读查询使用独立连接，不等待写入 |

融合编码不改变指纹：每项输出与不融合时的字节相同，融合与不融合求值结果在持续集成中的比对，计划随融合编码一并加入。

## 度量

- 每个派生在目录中记录其墙钟时间、CPU 时间、读写字节数，以及估算与实际的峰值内存。`sekai-exporter stats` 列出开销最大的派生类型，以及内存估算偏差最大的转换器。优化以这份记录为起点。
- 各热点在合成输入上设有基准测试。回归检查使用在共享机器上保持稳定的指令数，而非墙钟时间。
- 基于真实游戏数据的基准测试由持有数据的一方在本地运行，其结果不属于本仓库的内容。
