# 架构

[English](architecture.md)

本文说明导出器所依据的模型、结果的求值方式，以及代码划分为 crate 的方式。术语的定义参见[术语表](glossary.md)。

## 模型：内容寻址的派生图

导出的每一步都是纯函数，每一项输入与输出都以其内容标识。因此，批量导出、静态发布、按需导出、无服务器函数与浏览器内解包并非五套独立的系统，而是同一张函数图在不同地点、以不同策略求值的结果。存储是这张图的缓存，发布则是为其结果赋予名称。

模型中只有四种事物：

| 事物 | 定义 | 示例 |
|---|---|---|
| **输入** | 外部字节，以其哈希值标识 | 一个下载的资源包、客户端安装包中的一个 player data 文件、游戏数据表中的一条记录 |
| **派生** | `输出 = f(输入…)`，其中 `f` 为纯函数。派生的**指纹**为 `H(f 的名称与版本, 参数, 全部输入的哈希)` | `index(资源包)`、`convert(转换器, 闭包, 记录)`、`transform(编码器, 参数, blob)` |
| **绑定** | `(区服, 版本, 视图, 路径) → 某个派生的某个输出` | `jp/storage/character/member/x.png → transform(png, convert(image, …))` |
| **物化** | 将一组绑定以某种形状写入某处 | 一棵路径树、一份指向 store 的索引，或不写出任何内容 |

函数共有三种：

- **index** 读取一个资源包，产出其对象表与引用边。
- **convert** 将转换器应用于某个根对象的闭包及转换器读取的数据表记录，产出一个资产。
- **transform** 以固定参数将编码器应用于一个 blob，产出另一个 blob，例如将无损图片重新编码为某个视图所需的格式。

**视图**是产生绑定的函数。仅重排路径的视图即为一个路径模板；需要不同字节的视图则产生 transform 派生。

### 由模型推出的性质

| 性质 | 成立的原因 |
|---|---|
| 增量运行 | 指纹已有输出的派生不再重复计算 |
| 跨区服共享 | 指纹不含区服，两个区服中相同的内容具有同一指纹，只有一份输出 |
| 输出自描述 | 每个资产随附一份文档，记录其函数、版本、输入、输出以及每个文件的角色 |
| 目录可重建 | 派生记录与绑定承载了全部语义，目录只是一份可从 store 重建的索引 |
| 镜像可验证 | 任何人以相同输入重算某个派生，都会得到相同的哈希 |

## 身份

| 概念 | 定义 |
|---|---|
| 区服与来源 | `jp`、`en`、`tw`、`kr`、`cn`。来源为 `cdn`（下载的资源包）或 `client`（客户端安装包内的资产） |
| 版本 | 区服的资产身份与数据表身份，见[版本身份](sources.zh-CN.md#版本身份) |
| 资源包 | 清单中的 bundle 名称；`client` 来源为 `player` |
| 对象 | `(资源包, path ID)` |
| 类 | 原生类名。`MonoBehaviour` 为 `程序集/命名空间.类名`，经 `m_Script` 及其 `MonoScript` 解析，必要时跨文件解析 |
| 引用 | 每个 PPtr 解析为 `(资源包, path ID)`。外部文件经外部文件表解析到包含它的资源包。指向引擎内置资源的引用记为外部引用，不视为错误 |
| 逻辑路径 | 去掉 `assets/sekai/assetbundle/resources/<category>/` 前缀与扩展名的容器路径 |

资产以逻辑路径与资产形式命名，并位于其资源包同名的目录内：逻辑路径不在该目录内时，放到该目录下，写作 `<资源包>/<逻辑路径>`，因此名称只取决于资产自己的资源包。当多个资产将获得同一名称时，根对象属于不同类的资产按类优先级排序（先 `Texture2D`，再 `Sprite`，其他类按类名排序），除第一个以外的资产加 `@<类名>` 后缀；根对象属于同一类的资产按根对象的 `(资源包, path ID)` 排序，除第一个以外的资产加 `@<path ID>` 后缀，path ID 与对象文档一样写作十进制。两种后缀同时出现时，类名在前。同组资产若在不同资源包中有相同的 path ID，名称无法区分，按资产错误报告。结果只取决于该版本的索引，与工作完成的先后无关。同组任一成员发生变化时，整组名称重新确定。

## 求值

**策略。** *急切*求值预先计算全部绑定，[管线](pipeline.zh-CN.md)用流式求值器逐个资源包地完成这件事。*惰性*求值在请求到达某个派生时才计算，并缓存其结果。*混合*求值预先计算常被请求的绑定，其余按需计算。

**地点。** 单机批处理、自托管服务、运行 WebAssembly 核心的无服务器函数、运行同一核心的浏览器，或以库的形式使用各 crate 的其他程序。

**寻址方式**决定惰性求值所能达到的程度：

- **按资源包寻址**（`<区服>/bundle/<资源包名>/…`）：完全惰性。请求到达时取得资源包、解包并返回对象即可，无需预先准备任何索引。
- **按逻辑路径寻址**（`<区服>/<视图>/<逻辑路径>`）：须先将路径对应到其所在的资源包与对象，因此需要绑定索引。index 派生开销很小，采用急切求值；只有开销较大的 convert 与 transform 派生采用惰性求值。

惰性求值器与流式求值器一样，依据资源包的单元为该资源包的资产命名并计算指纹，写出相同的文档与成员。一次请求只打开所在资源包的窗口，只从该资产闭包中的资源包读取对象字节。同一指纹的并发请求只计算一次。请求可以指定资产名字，也可以指定资源包与对象。

在 `wasm32` 上，核心可以产出贴图、精灵、FLAC 音频、文本、字体、剧本、Live2D 模型与动作集以及服装部件与动作，结果与原生输出逐字节相同。视频需要 `ffmpeg` 程序，报告 `encoder_unavailable`。估算内存超过 2 GiB 的资产报告 `too_large`。

## 模型所依赖的约束

1. **确定性。** 转换器与编码器不读取时钟，不依赖线程顺序，不遍历无序容器。相同的输入在单线程与多线程下、原生构建与 `wasm32` 下、启用与不启用[性能](performance.zh-CN.md)一文所述的优化时，均产生相同的字节。持续集成对这三组条件逐一检查。
2. **核心为纯 Rust。** 解包、解码与转换相关的 crate 均可编译到 `wasm32`。以 C 编写的库仅限于编码 crate，且仅用于原生构建。某个派生所需的后端在当前目标上不可用时，该派生以具名错误失败，而不替换为其他后端，因为不同的后端会产生不同的字节。
3. **声明开销。** 每个转换器声明其开销等级。闭包过大、无法在无服务器函数中运行的转换器声明为仅限批处理，对其发出的惰性请求以名称拒绝。
4. **输入保留。** 惰性求值要求输入在之后仍可获取，而游戏的分发服务器不保留旧版本。需要历史版本的部署应按配置保留输入或输出之一。
5. **凭据只存在于部署端。** 账号与密钥由部署导出器的一方配置，永不进入仓库。参见[来源](sources.zh-CN.md)。

## 转换器契约

转换器须声明：

- 所接受的根对象，以类与逻辑路径描述；
- 所读取的游戏数据表；
- 所产出的资产形式，以及定义该形式的 [`docs/spec/`](spec/) 规范；
- 其版本，以及开销等级（轻、重或宽，决定其编码占用几个 CPU 槽位）与所需内存的估算值。

转换器接收一个根对象与一个上下文，通过上下文读取被引用的对象、载荷字节与数据表记录，并返回资产的各个成员及其角色：成员或为已解码内容（图像面、PCM 采样），由求值器编码；或为成品字节。资产文档由求值器写出。转换器不读取文件、不选择输出路径、不写入目录，这些职责均由求值器承担。

转换器无法产出正确的资产时，对该资产报告具名错误，运行继续处理其他资产。转换器未编译进构建时，其本应产出的资产报告为错误 `not_compiled`。

## Crate

工作区由十四个 crate 组成，平铺于 `crates/` 目录下。crate 边界只设在以下位置：依赖集合不同（C 库、网络、目录数据库）、存在大块可选代码，或存在被多个 crate 使用的稳定接口。其余部分均为由 feature 启用的模块。

| 层 | Crate | 内容 |
|---|---|---|
| 0 | `sekai-unity` | 解包：UnityFS、SerializedFile、type tree、布局编译、块缓存。不使用过程宏，不依赖 C 库 |
| 0 | `sekai-format` | 已发布文档的 serde 类型，使用者可将其作为 git 依赖直接使用 |
| 1 | `sekai-layouts` | 不带 type tree 的对象所用的字段布局表及其加载 |
| 1 | `sekai-codec` | 纯 Rust 实现的贴图与 CRI 解码 |
| 1 | `sekai-catalog` | 内容寻址的 store 与目录 |
| 1 | `sekai-game` | 本游戏专有的输入：资源包去混淆、清单、下载、游戏数据表、区服配置。`cdn` feature 通过 `rustls` 与 `ring` 提供 TLS，其中含 C 与汇编 |
| 2 | `sekai-convert` | 转换器接口、写出器与通用转换器 |
| 2 | `sekai-encode` | 已解码内容的编码器。规范形式的编码器为纯 Rust 且始终存在；编码器的全部 C 依赖限于此处，每项一个 feature |
| 2 | `sekai-publish` | 布局、store、发布协议与资产列表 |
| 3 | `sekai-pipeline` | 流式与惰性两种求值器及调度器。已有输出的派生由目录（数据库或内存中）复用 |
| 3 | `sekai-moesekai` | 剧本、剧集、虚拟演唱会、服装与 storage 视图 |
| 3 | `sekai-mysekai` | 按复刻游戏的运行时所需的完整形式产出的 MySekai 资产 |
| 4 | `sekai-exporter` | 命令行程序 |
| 4 | `sekai-wasm` | 面向 JavaScript 暴露的核心 |

依赖只指向更低的层。转换器返回已解码的内容（图像表面、PCM 采样）或成品字节；对已解码内容的编码是一个独立的变换派生，因此 `sekai-convert` 不依赖 `sekai-encode`。转换器族、视图与后端均为由 feature 启用的模块，参见 [Feature](features.zh-CN.md)。
